> 筆者（青木 博資）がAI社員（Claude / Codex）と運営する一人会社KADOの実例です。AI社員が執筆し、筆者が事実確認と最終確認をしています。

**AIエージェント**：役目と指示を受けて、自分で仕事を進めるAIです。  
**検証**：できあがった物が、条件や元の資料と合うかを確かめることです。  
**リポジトリ**：仕事のファイルと、その変更の記録をまとめて置く場所です。

Claude CodeやCodexへ仕事を任せると、毎回の指示だけでは決めきれないことがあります。支出、外部への送信、成果物の確認、AIモデル変更の記録などです。

KADOでは、会社に共通するルールを、最上位の `CLAUDE.md` に「社則」として書きました。

## なぜ社則が要るのか

![会社共通の社則と事業ごとの情報を分ける](/images/kado-x10-rules-and-divisions.png)

KADOは事業より先に、組織と仕事の流れを作りました。制作手順が変わっても、支出の権限、承認の正本、独立した確認、機密の扱いは簡単に変えないためです。

- `CLAUDE.md`：会社に共通する権限・組織・記録・検証の境界
- `divisions/`：事業ごとの目的・情報・制作手順
- 社則が決めること：AIが自分で進めてよい範囲、人間へ戻す判断、記録場所
- 社則ではないもの：作業の細かい手順を集めただけの文書

## 10のルール

`§0` から `§9` まで、実数は10項目です。

![会社を動かす10のルール](/images/kado-x10-ten-rules.png)

### §0 会社の目的を一文にする

> CEOの判断力を、AI社員の調査・制作・検証・運営で拡張し、複数事業を少ないCEO稼働で回す。

- 成果物が増えても、人間の判断の負担が増え続ければ目的に反する
- 人間を外すのではなく、判断材料を作る仕事をAIへ渡す

### §1 理由を記録する

方向に関わる決定は、次の6点を意思決定の記録へ残します。

- 結論
- 選択肢
- 各案の根拠
- 採用案
- 採用理由
- 日付

理由がなければ未決定として扱います。採用案だけでは、次のAIが却下した案をもう一度出したり、大切な制約を古いものとして消したりするためです。

### §2 提案と実行の権限を分ける

![AIが提案し、人間が承認して実行する境界](/images/kado-x10-authority-gates.png)

| 行為 | ルール |
|---|---|
| 支出・契約・サブスク | AIは提案まで。CEOが承認し、自ら実行する |
| 外部送信 | AIは下書きまで。CEO承認後に送信する |
| Discordへの投稿 | 社内向けのため承認不要。機微情報は載せない |
| 定期実行の増設・モデル配置の変更 | 稟議と意思決定記録を残す |
| 権限・APIキーの追加 | CEOが手で行う。AIは自分の権限を広げない |

**APIキー**：外部サービスを使う人や仕組みを確かめる、秘密の文字列です。

- 端末に認証情報やCLIが見えても、持ち主と利用可否を確かめるまで使わない
- 「使える」と「使ってよい」は別
- 承認の正本は、チャットではなく `office/approval-queue.md`
- 流れる会話と、後から読み直せる承認の記録を分ける

**CLI**：文字の命令で道具を動かす仕組みです。

### §3 作る役と疑う役を分ける

この会社では、作る役を「実行役」、疑う役を「検証役」と呼びます。

| 指揮する役 | 仕事の分け方 |
|---|---|
| CEO | 全体の責任を持つ |
| COO（業務進行） | 実行役 + 検証役 |
| CRO（リサーチ） | 実行役 + 検証役 |
| CPO（制作） | 実行役 + 検証役 |
| 監査役（独立） | 実行役 + 検証役 |

![計画、実行、独立確認、報告の流れ](/images/kado-x10-work-and-records.png)

1. 参謀が計画する
2. 実行役が作業する
3. 検証役が、実行時の会話を見ずに成果物だけを独立して確かめる
4. 参謀が報告する

- 実行役と検証役は、できるだけClaudeとCodexの別系統にする
- 監査役は、業務進行の指揮から独立させる

### §4 稟議を紙面にする

承認依頼はチャットの一言で済ませません。一枚の紙面に、判断に必要な物をまとめます。

- 前提知識
- 何を、なぜ行うか
- 選択肢と評価の軸
- 推す案と、その理由
- 費用
- 見送った場合に起きること
- 承認してほしいこと

「承認だけを行う」とは、選択ボタンだけを渡すことではありません。AIが判断材料を整え、人間が決定に集中する分業です。

### §5 記録と読みやすい窓口を分ける

| 層 | 役目 |
|---|---|
| リポジトリ書類 | 記録・承認・今の状態を持つ正本 |
| Discordの経営会議室 | 日次報告や会議の要約 |
| 社内ラジオ・週刊社内報 | 空き時間に状況を追う窓口 |

- チャットや音声には、金額・顧客名・認証情報・個人情報を載せない
- 要約と、正本への相対パスだけを置く

**相対パス**：今いる場所を出発点にした、ファイルまでの道順です。

### §6 自動化の本数を管理する

- 最初は、日次朝会1本と週次経営会議1本
- やることがない日は「特記なし」で終える
- 監査役が毎月、モデル別の実測消費・空回り率・社則違反を調べる
- 本数や回数を変える時は、稟議にかける

定期実行は、続けて権限と計算資源を使います。小さな実装変更と同じ感覚では増やしません。

### §7 モデル配置を人事として扱う

**モデル**：ClaudeやCodexなど、AIの頭脳の種類や版です。

- 配置の台帳は `org/model-assignment.md`
- 変更は、稟議 → 意思決定の記録 → エージェント定義の順で反映する
- 役職名だけでなく、仕事の種類・ツール接続・実行役と検証役の組み合わせで決める
- 定額の利用枠と実際の消費を見て、主力配置を変える
- 理由と履歴を残し、新しいモデルが出た後も変更結果を確かめられるようにする

### §8 正本の場所を固定する

次の情報には、それぞれ一つの置き場所を決めます。

- 現在の状態
- 承認待ち
- 意思決定
- 朝会ログ
- 週次議事録
- 稟議の紙面
- 事業部の情報

AIにとって「どこかに書いてある」は、書いていないのと近い状態です。保存先の決まりがあれば、次の担当が現在地と未決のことを戻せます。

### §9 表示ではなく実体を検証する

- ツールが実際に返した値だけを事実とする
- 成功メッセージだけで判断せず、ファイルの存在と中身を見る
- 集計は計算し直す
- 公開物は、隠すべき情報が残っていないかを見る
- 独立した検証役が確かめる
- 実データは隠すことを前提に、必要な分だけ取得する
- 実データは確認後に消す
- 機密はリポジトリへ書かず、対象外にした環境変数ファイルへ置く

**環境変数**：認証情報などを、ファイル本文に書かず実行時に渡す入れ物です。

これは注意力だけの話ではありません。「何を見たら完了か」を、だれでも確かめられる形にするルールです。

## 運用後に変えた3点

### 1. チャットでの承認を無効にした

- 承認の記録にない物は、未承認として起票し直す
- 例外を後から足し、正本を二つにしない
- `起票 → CEO承認 → 意思決定の確定` の順にする

### 2. 承認をなくさず、大きさを変えた

- 複数の公開物を一枚の稟議にまとめる
- 決めた範囲内の制作と修正を、まとめて承認する
- AIが動ける範囲を広げても、承認そのものは残す

### 3. 公開前のCEO目視を残した

- AIが機密を隠せたか確かめることと、人間の最終確認は置きかえられない
- 制作中に任せる範囲を広げても、外部公開の責任は人間が持つ

## 移す時のチェックリスト

- [ ] 目的を、人間とAIの分業として一文で書いたか
- [ ] AIが提案までできる行為と、実行できる行為を分けたか
- [ ] 承認の正本を一つに決め、チャットとの関係を決めたか
- [ ] 決定に選択肢、根拠、採用理由、日付を残すか
- [ ] 計画、実行、独立検証、報告の受け渡しを決めたか
- [ ] 定期実行の本数、終了条件、増やし方を決めたか
- [ ] 外部公開、支出、契約、権限追加を人間へ戻すと書いたか

最初から長い社則は要りません。事故のたびに注意書きを増やすのではなく、あいまいだった権限、正本の場所、次に見る完了条件を社則へ戻します。

`CLAUDE.md` を指示文置き場ではなく、組織が次にどう動くかを決める文書として扱えば、AIエージェントが増えても人間の責任の範囲はぼやけません。
